System Files

Kali Linux

Kali is an assessment box, so the most sensitive data on it is usually your client's: captured hashes, cracked passwords, dumps and traffic. This page maps where Kali and its tools keep that data, how the system is set up, and how to keep the box clean and secure.

Overview

Key facts about the current Kali release and how it differs from a general purpose distribution.

Current releaseKali 2026.3, released 26 October 2026, with Linux 7.1 and Xfce as the default desktop (GNOME and KDE Plasma 6.7 optional). Based on Debian testing.
Support statusRolling distribution on the kali-rolling branch. Quarterly releases are snapshots, and only an up to date system is supported. Upgrade with apt full-upgrade, no reinstall needed.
Default user modelNon-root user since 2020.1. The installer asks for a user. Prebuilt VM, cloud and live images use kali / kali. Root has no password and is reached with sudo. Default shell is zsh.
File systemext4 by default. The installer offers LVM with LUKS full disk encryption. Live USB images support encrypted persistence with LUKS.
Built-in security featuresNetwork services such as SSH, PostgreSQL and Apache are installed but disabled by default. Signed repository (archive key rotated in April 2025). kali-tweaks for hardening and protocol compatibility settings.
Where logs livesystemd journal (journalctl, stored in /var/log/journal/). Text files such as /var/log/auth.log only exist when rsyslog is installed. Tool output lands in your home folder, tool folders under /usr/share/ and the current working directory.

Warning: Only use Kali tools against systems you own or have written permission to test. Treat everything the tools collect as confidential client data.

Hardening Checklist

How to keep an assessment box secure during the job and clean after it.

  • Verify the ISO or image checksum against the signed SHA256SUMS from kali.org before installing.
  • Change the kali password on prebuilt images, and do not enable passwordless root with kali-grant-root on engagement machines.
  • Use full disk encryption (LUKS) for installs and encrypted persistence for live USB. Encrypt VM disks on the host.
  • Update with sudo apt update && sudo apt full-upgrade before every engagement. Keep only Kali repositories and never add Debian or Ubuntu sources.
  • Keep network services off. Enable SSH, PostgreSQL, Neo4j or web servers only when needed, bind them to localhost where possible, and stop them afterwards.
  • Change the default Neo4j and BloodHound admin passwords during setup.
  • Run a host firewall on client and public networks and allow only the listeners you need for the test.
  • Prefer packaged tools. Review GitHub tools before running them, keep them in /opt or a venv, install Python tools with pipx and avoid sudo pip.
  • Use one VM snapshot, one Metasploit workspace, one NetExec workspace and one project folder per client.
  • Keep your own activity log (for example the script command or tmux logging) with UTC timestamps for the report.
  • After the job, archive the evidence encrypted, then wipe ~/.msf4/loot, ~/.nxc, Responder logs and Responder.db, sqlmap output, potfiles, tickets, captures, browser profiles and history, or revert the VM to a clean snapshot.
  • Do not reuse the same box across clients without that clean up. Data from one client must not reach another.
